# Results, not tool lists, drain binary-mcp's context

binary-mcp's largest token cost is what its tools return, not the 147 definitions it advertises, so the first fixes belong in result shaping. Measured with OpenAI's o200k tokenizer as a stand-in for Claude's unpublished one, the full `tools/list` is **about 43.4K tokens** (36.5K of it in the fields a Claude tool definition carries) and sends no server instructions, while a single `decompile_functions` call at its default budget can return **about 46K tokens** on its own. Every result is then re-read on each later request until compaction, which Claude Code postpones to roughly 967K tokens on 1M-context models. Claude Code now defers all MCP tool definitions behind tool search by default, so there the list costs little more than 147 names; it still costs its full size in clients that load tools upfront, and at 147 tools it exceeds the hard caps in VS Code (128 per request), Windsurf (100) and, by forum reports, Cursor (about 40). Four result-side changes deliver most of the saving: switch off FastMCP's auto-generated output schema on the 137 string-returning tools, which doubles wire size today and makes Codex, VS Code and (by user reports) Claude Code read JSON-escaped Markdown; cap every code-returning tool at one budget of about 24,000 characters instead of 120,000; state the 109-token untrusted-data notice once in new server instructions instead of in every wrapped block; and make one-line tabular rows the default for listings, which cuts them by **50-84%**. On the definition side, deleting docstring `Args:`/`Returns:` sections and audit history, collapsing Optional schemas, dropping the output schemas and registering the disabled raw WinDbg tool only when its flag is set take the list from about 43K to **roughly 20-25K tokens**, and registering WinDbg only on Windows plus startup toolset profiles lets the server fit capped clients. Every recommended change keeps the tool list fixed for the life of a process, which protects prompt caching, while the evidence argues against runtime tool toggling, an arbitrary-code tool sitting next to attacker-authored sample data, and MCP sampling, which the 2026-07-28 specification deprecates. All counts are proxies, and Anthropic says its tokenizer since Claude 4.7 produces about 30% more tokens than earlier Claude models, so the plan starts with a token-budget test checked against Anthropic's free `count_tokens` endpoint.

## Caching makes the tool list cheap and resident results expensive

Every binary-mcp figure in this report comes from a measured audit of the repository at commit f4595aa, whose `src/` tree is unchanged at the current HEAD. The audit captured `tools/list` and tool results in the exact stdio wire format through an in-memory FastMCP client, ran the triage tools on three benign PE files, and ran the Ghidra-backed tools against a synthetic analysis cache written through the server's own `ProjectCache`, so Ghidra-derived result sizes are estimates for real binaries ([measurement script](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/scripts/measure_results.py); [tools/list analysis](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/run1_analysis_summary.txt)). Counts use o200k because Claude's tokenizer is unpublished, and Anthropic says the tokenizer used since Claude 4.7 produces "approximately 30 percent more tokens" than earlier models for the same text ([Claude token counting docs](https://platform.claude.com/docs/en/build-with-claude/token-counting)), so absolute figures probably understate Claude's counts and the relative savings are the better guide. The audit also found that the common characters-divided-by-four rule holds for prose but **undercounts pseudocode by about 35%**, because decompiled C runs at roughly 2.6 characters per token ([results summary](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/results_summary.json)). Any character budget the server sets has to be read with that ratio in mind.

Prompt caching treats tool definitions as the first segment of the cached prefix, ahead of the system prompt and the messages, and a change to any tool's name, description or parameters invalidates all three layers ([Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Cache reads cost 0.1× of base input on most models and **0.05× on Opus 5.5 and Sonnet 5.5**, while a five-minute cache write costs 1.25×, so on Opus 5.5 an invalidation costs 25 times a cached re-read: about $0.75 instead of $0.03 to reprocess a 150K-token context (same source; this report's arithmetic). Claude Code keeps the tool list from a conversation's first request for the whole conversation when tool search is on, but when tools load upfront, a server connecting or "a dynamic tool update" invalidates the cache ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)). binary-mcp is already in good shape on this front: two processes with different hash seeds and very different environment variables produced a **byte-identical** `tools/list` ([run 1](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/run1_tools.json); [run 2](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/run2_tools.json)), which is what the 2026-07-28 specification now asks for when it tells servers to return tools in a deterministic order to improve prompt-cache hit rates ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Manus's "mask, don't remove" lesson, that removing tools mid-task breaks the cache and confuses the model, is about churn inside a session ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). A list that differs between a Windows host and a Linux host, but never changes inside one process, does not run into it.

Caching makes the fixed list cheap in dollars and moves the bill to results that stay resident. On Opus 5.5, at $4 per million input tokens ([Anthropic prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)), a block of N tokens that stays in context for k more requests costs N × (1.25 + 0.05k) × $4 per million, so the re-reads overtake the one-time write after only 25 requests. Applied to the audit's numbers (this report's arithmetic), a client that loads binary-mcp's 36.5K model-facing definitions upfront pays about **$2.37** for them across a 300-request session. One 10-function `decompile_functions` result of 11.1K tokens that stays resident for 200 requests costs about **$0.50**, against about $0.03 for a 600-token header plus a handle, so ten such results kept from early in a session cost twice the whole tool list. In Claude Code, which loads only "tool names and server instructions" at session start ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)), the definition side shrinks to names and results become effectively the whole MCP bill.

Results stay resident for a long time because compaction is late and lossy. Claude Code compacts native 1M-context models at "about 967K tokens by default" ([Claude Code model configuration](https://code.claude.com/docs/en/model-config)), and after compaction "full tool outputs and intermediate reasoning are gone", while Claude Code re-reads the files modified most recently, not MCP results ([Claude Code context window](https://code.claude.com/docs/en/context-window)). Whether Claude Code's automatic clearing of old tool results ever touches MCP results is undocumented, and third-party write-ups list only built-in tools ([ClaudeLog](https://claudelog.com/faqs/what-is-micro-compact/)), so binary-mcp should assume its results stay until full compaction. Two design rules follow. Results should be small, because size times residency is the cost. And results should carry short, stable handles, such as an address plus a content hash, because a handle is what a compaction summary keeps and what lets the model re-fetch cheaply from binary-mcp's analysis cache. That cache, like FastMCP's `ResponseCachingMiddleware`, which stores and replays whole responses ([FastMCP caching middleware](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/middleware/caching.py)), saves Ghidra time but **not tokens**, because a cached result still reaches the model in full.

The stakes go beyond dollars. Chroma's study of 18 models found performance "grows increasingly unreliable as input length grows" even on deliberately simple tasks ([Chroma, Context Rot](https://trychroma.com/research/context-rot)), echoing the older finding that models use information in the middle of long inputs worst ([Liu et al., Lost in the Middle](https://arxiv.org/abs/2307.03172)). For tools, Anthropic's documentation says Claude's ability to pick the right tool "degrades once you exceed 30-50 available tools" ([Claude tool search docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)), and its internal evaluations had tool search raising Opus 4 from **49% to 74%** and Opus 4.5 from 79.5% to 88.1% while cutting definitions from about 77K to 8.7K tokens ([Anthropic, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). The RAG-MCP stress test found tool-selection accuracy of 13.62% with every schema in the prompt against 43.13% with retrieval ([RAG-MCP](https://arxiv.org/abs/2505.03275)). These are vendor-internal or synthetic results, but they agree in direction: fewer resident tokens and fewer visible tools help selection as well as cost.

Anthropic's context-engineering guidance names the levers: keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and load data just in time, clear old tool results as "one of the safest lightest touch forms of compaction", keep structured notes outside the window, and delegate to sub-agents that return "a condensed, distilled summary of its work (often 1,000-2,000 tokens)" ([Anthropic, effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Anthropic reports that context editing cut token use by **84%** on a 100-turn evaluation, a vendor number ([Claude blog, context management](https://claude.com/blog/context-management)). Claude Code offers client-side versions of each: subagents keep verbose output in their own windows ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)), skills cost about 100 tokens of metadata until triggered ([Agent Skills overview](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)) and plugin skills and hooks never invalidate the cache ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)), and hooks can replace an MCP result before Claude sees it or re-inject state after compaction ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). None of this is portable, and the one protocol-native route for server-side summarization, MCP sampling, is deprecated as of the 2026-07-28 revision ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) and, per a 2026 client survey, still unsupported in Claude Code ([Developers Digest](https://www.developersdigest.tech/blog/mcp-client-features-explained-2026)). The portable baseline is therefore server-side shaping. binary-mcp already keeps a structured note in its coverage ledger, but `load_full_session` replays every stored output in full, **20,149 tokens for five calls that originally cost 20,161** ([what-if measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/whatif.json); [server.py:5385](../src/server.py#L5385)), which is the opposite of just-in-time retrieval.

## Docstring prose and always-on debuggers fill most of the 43K-token list

Published measurements put MCP definitions at hundreds to thousands of tokens per tool: Anthropic's reference setup ranges from about 740 tokens per tool for GitHub's server (35 tools, about 26K) to about 1,900 for Slack's (11 tools, about 21K), and Anthropic has seen 134K tokens of definitions before optimization ([Anthropic, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). binary-mcp sits at about 295 tokens per tool: its `tools/list` is **178,213 bytes and 43.4K o200k tokens**, unpaginated, with no server instructions because the app is built as a bare `FastMCP("binary-mcp")` ([tools/list analysis](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/run1_analysis_summary.txt); [server.py:119](../src/server.py#L119)). Some peers are far leaner per tool: bethington's Ghidra server measured 251 tools at 18,385 tokens including input schemas, about 73 per tool ([bethington Context-Window-Analysis.md](https://github.com/bethington/ghidra-mcp/blob/cf8b12db27eb139b28b90eaa3488306da910d759/docs/Context-Window-Analysis.md)). The split by field shows where binary-mcp's bytes go.

| Field in each tool | o200k tokens | Share of list | Reaches a Claude model? |
|---|---:|---:|---|
| `description` (the raw docstring) | 27,100 | 62.5% | Yes |
| `inputSchema` | 8,365 | 19.3% | Yes |
| `outputSchema` (auto-generated by FastMCP) | 4,377 | 10.1% | Unverified; probably not, since Claude's tool format has no such field |
| `_meta._fastmcp.tags` | 2,518 | 5.8% | Unverified; probably not |
| `name` | 978 | 2.3% | Yes |

Source: [tools/list analysis](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/run1_analysis_summary.txt). The last column follows from Claude's tool definition, which carries only a name, a description and an input schema ([Claude API, define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)).

Descriptions dominate because FastMCP 2.14.7 sends the whole docstring, `Args:` and `Returns:` included, as the description, and builds parameter descriptions only from `Annotated`/`Field` metadata ([FastMCP tool.py](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py)). binary-mcp's contributor template mandates exactly those Google-style sections ([CONTRIBUTING.md](../CONTRIBUTING.md#L226)), so 114 tools carry an `Args:` block while **none of the 439 schema properties has a description**; deleting the `Args:`, `Returns:`, `Examples:` and `Notes:` sections would save **12,866 tokens (29.7%)**, and keeping only first paragraphs would save 25,160 (58%) ([tools/list field analysis](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/run1_analysis.json)). The heaviest descriptions narrate history rather than usage. `analyze_binary` spends 1,333 tokens on its description, and `windbg_execute_command`, which refuses to run unless `BINARY_MCP_ENABLE_RAW_WINDBG=1`, still lists 1,319 tokens that are mostly a security essay citing "audit finding F-6" ([wire dump](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/run1_tools.json)). Pydantic's rendering of 179 Optional parameters as `anyOf [X, null]` plus `default: null` adds **2,165 tokens (5.0%)**, with 17 such parameters on `x64dbg_breakpoint` alone (same source). And the 49 debugger tools, 32% of the list, are registered on every host: WinDbg's 33 tools (6,225 tokens) check `_is_windows()` inside each body and answer "WinDbg tools require Windows with Pybag installed" at call time ([windbg_tools.py:41](../src/tools/windbg_tools.py#L41); [server.py:6327](../src/server.py#L6327)).

Trimming has a floor, though. Anthropic calls detailed descriptions "by far the most important factor in tool performance" and asks for "at least 3-4 sentences" on what a tool does, when to use it and when not to, and its caveats ([Claude API, define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). Deferral sharpens that advice rather than weakening it: Claude's tool search matches tool names, descriptions, argument names and argument descriptions ([Claude tool search docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)), and Claude Code matches only within the first 4,096 characters of a description and tells authors to "put the words Claude would search for near the start" ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). The right cut is duplication and non-usage prose, not meaning. Parameter text should move into `Field(description=...)`, where search indexes it; `Returns:` blocks, the 53 restated defaults and the audit narration should go; and each description should keep a keyword-dense first sentence plus a when-not-to-use line that names the sibling tool, which matters in a catalog where several tools hand back pseudocode under names that do not say so ([tool_catalog.py](../src/tool_catalog.py)). pyghidra-mcp shows the aggressive end of the range: it reduced its manifest by about 66% by cutting docstrings to one or two sentences and dropping `Args:` sections ([pyghidra-mcp commit 44ee2c2](https://github.com/clearbluejar/pyghidra-mcp/commit/44ee2c2fd784ce9e4210a101f6a80836c4a1263f)).

Discoverability is the other half of the definition problem. Under Claude Code's default, the model sees 147 bare names and no instructions, although Claude Code's docs say server instructions "become more useful with tool search enabled" and should explain what tasks the tools handle and when to search for them, within 4,096 characters ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). Tool search returns five tools per query by default ([Claude tool search docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)), so one search cannot load the 33-tool `windbg_` family, and the Ghidra and .NET tools share no name prefix for a regex query to match. A server can also mark a few entry tools to load upfront with `_meta["anthropic/alwaysLoad"]`, which FastMCP 2.14.7 passes through from `@tool(meta=...)` ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp); [FastMCP server.py](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/server.py)). GitHub's MCP server is a working model: it generates instructions from its enabled toolsets, including "Context management" advice to page in batches of 5-10 items ([github-mcp-server instructions.go](https://github.com/github/github-mcp-server/blob/main/pkg/inventory/instructions.go)).

Clients without deferral, or with caps, pay the full list. VS Code Copilot sets `HARD_TOOL_LIMIT = 128` and groups the overflow into experimental "virtual tools" ([vscode-copilot-chat configurationService.ts](https://github.com/microsoft/vscode-copilot-chat/blob/main/src/platform/configuration/common/configurationService.ts)); with about 40 built-in tools competing for that budget ([GitHub blog, fewer tools](https://github.blog/ai-and-ml/github-copilot/how-were-making-github-copilot-smarter-with-fewer-tools/)), roughly 88 MCP tools fit, by inference. Windsurf documents "a maximum limit of 100 tools" across all servers ([Iterable MCP PR #19, quoting Windsurf's docs](https://github.com/Iterable/mcp-server/pull/19/files)), 2025 forum threads report Cursor sending only the first 40 tools ([Cursor forum](https://forum.cursor.com/t/tools-limited-to-40-total/67976)), and Claude Code itself loads every tool upfront when tool search is off, for example behind a non-first-party `ANTHROPIC_BASE_URL` gateway ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). The proven answer is a startup profile. GitHub's server takes `--toolsets`, `--tools`, `--exclude-tools` and `--read-only` ([github-mcp-server configuration](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md)), estimates a 60-90% context cut from loading 3-10 tools ([GitHub changelog](https://github.blog/changelog/2025-12-10-the-github-mcp-server-adds-support-for-tool-specific-configuration-and-more)), and no longer ships its old runtime `--dynamic-toolsets` mode ([github-mcp-server](https://github.com/github/github-mcp-server)). FastMCP 2.14.7 already supports profiles through `include_tags` and `exclude_tags`, which filter at construction and also block calls to excluded tools ([FastMCP server.py](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/server.py)), and binary-mcp's catalog already tags every tool with a `category:` ([tool_catalog.py:101](../src/tool_catalog.py#L101)).

Runtime alternatives fare worse for this server. Toggling tools mid-session with `list_changed` invalidates the cache in upfront clients, and Cursor staff say it "doesn't fully support the listChanged subcapabilities" ([Cursor forum](https://forum.cursor.com/t/doubts-regarding-the-capabalities-negotiations/147888/2)). Server-side search facades report the largest cuts, up to 160× for Speakeasy's dynamic toolsets and 70-97% for Atlassian's mcp-compressor, both vendor claims ([Speakeasy](https://www.speakeasy.com/blog/how-we-reduced-token-usage-by-100x-dynamic-toolsets-v2); [Atlassian](https://www.atlassian.com/blog/developer/mcp-compression-preventing-tool-bloat-in-ai-agents)), but they put every tool behind one `invoke` name, which breaks Claude Code's per-tool permission rules and the PreToolUse gating that binary-mcp's `code-output` facet exists to support. The MCP specification will not settle the question: proposals for tool groups, lazy schemas and a `tools/search` method were all closed without entering the spec, and the 2026-07-28 client guide treats progressive discovery as the host's job ([SEP-1300](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1300); [MCP client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices)). On granularity, Anthropic now advises grouping related operations "into a single tool with an `action` parameter" ([Claude API, define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)), and the MCP-GRANITE study, known here only from search summaries, found that a middle granularity of about four tools beat both fine-grained and monolithic designs for 8 of 9 models ([MCP-GRANITE](https://arxiv.org/pdf/2609.24161)). GhidrAssistMCP went the other way, replacing 49 consolidated tools with 100 explicit ones because "Names carry the user's intent instead of requiring the model to discover a format/action selector" ([GhidrAssistMCP modernization review](https://github.com/symgraph/GhidrAssistMCP/blob/b575acc1412cafcfd4dc9fedb7f99ecf219c68ab/docs/modernization-review.md)). binary-mcp's x64dbg surface already sits in the middle, with 16 op-dispatch tools fronting 159 operations ([test_x64dbg_tool_groups.py:76](../tests/test_x64dbg_tool_groups.py#L76)); its 33 WinDbg tools do not.

The most radical option, code mode, is a poor fit. Hex-Rays' official IDA server exposes only six tools built around `execute_python` ([HexRaysSA/ida-mcp metadata snapshot](https://github.com/HexRaysSA/ida-mcp/blob/df6de7985b534a964c125d5a86e41b26b17b14f6/tests/snapshots/mcp_metadata.json)), Cloudflare reports a 99.9% definition cut for a 2,500-endpoint API ([Cloudflare, Code Mode](https://blog.cloudflare.com/code-mode-mcp/)), Anthropic describes an illustrative 98.7% cut for a code-execution workflow ([Anthropic, code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)), and programmatic tool calling saves 20-40% on typical traffic ([Claude programmatic tool calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)). But programmatic calling cannot call tools "provided by an MCP connector", every variant needs a sandbox, and the same docs warn that tool results "can contain any content, including code snippets or executable commands" (same source). binary-mcp's outputs are authored by malware and its stated posture is that "no tool can launch a binary" ([server.py module docstring](../src/server.py#L1)), so server-side composite tools capture the round-trip savings without the risk.

## Results arrive escaped, padded and past client inline limits

Anthropic's guidance for tool results is to combine "pagination, range selection, filtering, and/or truncation with sensible default parameter values", to steer the agent when truncating, and to offer a concise response mode; its own example fell from 206 to 72 tokens ([Anthropic, writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). binary-mcp applies parts of this, with concise modes on four tools and limits on most listings, but the measurements show five places where tokens leak.

### FastMCP sends each result twice, and three major clients read the escaped copy

Since FastMCP 2.10, a tool annotated `-> str` gets an auto-generated output schema `{"result": string}` marked `x-fastmcp-wrap-result`, and every call returns the text in `content` and again as `structuredContent` ([FastMCP tool.py](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py); [FastMCP tools docs](https://gofastmcp.com/servers/tools)). binary-mcp sets no `output_schema` anywhere, so 137 tools carry the wrapper and the 10 dict-returning coverage and job tools duplicate their JSON the same way; across 86 measured calls the wire carried **2.16 times** the text, and `get_functions(limit=100)` sent 15,285 tokens to deliver 7,017 ([results summary](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/results_summary.json)). Which copy reaches the model depends on the client. VS Code's source takes structured content "in place of any textual description when present" ([VS Code MCP tool contribution](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts)), Codex serializes `structuredContent` whenever it is present ([Codex models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/models.rs)), and Claude Code reportedly forwards only `JSON.stringify(structuredContent)`, according to an open issue with reports from versions 2.1.222 to 2.1.296 and no official documentation of the rule ([claude-code #79944](https://github.com/anthropics/claude-code/issues/79944)). Gemini CLI reads `content` instead ([Gemini CLI mcp-tool.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/tools/mcp-tool.ts)). On the first three clients, binary-mcp's Markdown therefore arrives as an escaped JSON string, which costs **11% more tokens on a 43-line Ghidra function** and 5.7% more on a 100-row table and replaces real newlines with `\n` escapes ([format measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/scripts/measure_out.txt)). Setting `output_schema=None` removes both the schema and the duplicate, and in this research's test on FastMCP 2.14.7 a two-hook middleware that strips both cut a 22,974-byte call result to 11,499 bytes ([FastMCP tool.py](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py)). Binary Ninja's MCP guidance states the principle plainly: "Return one representation" ([Binary Ninja MCP tool guide](https://github.com/Vector35/binaryninja-api/blob/dev/docs/dev/mcp-tools.md)).

### The default decompile budget is more than twice Claude Code's spill threshold

`decompile_functions` defaults to `max_body_chars=120000` ([server.py:3337](../src/server.py#L3337)), which at about 2.6 characters per token is **roughly 46K tokens**; 50 synthetic functions measured 43,471 ([results summary](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/results_summary.json)). The inline limits of the main coding clients all sit below that. Claude Code warns above 10,000 tokens, caps MCP output at 25,000 tokens, and saves any successful text result longer than **50,000 characters** to a file, replacing it with a path ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)); OpenCode cuts at 2,000 lines or 50 KB ([OpenCode PR #51200](https://github.com/anomalyco/opencode/pull/51200)), Gemini CLI truncates at 40,000 characters ([Gemini CLI configuration](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md)), Codex reportedly at 10,000 tokens, and VS Code truncates with a recovery hint that, per an open issue, cannot work ([vscode #311068](https://github.com/microsoft/vscode/issues/311068)). A maxed call therefore never reaches the model as written, and binary-mcp's note naming the withheld functions is appended at the end of the response ([server.py:3492](../src/server.py#L3492)), exactly where head-truncating clients cut first. Spill files are no reliable fallback: the Claude Agent SDK was reported to write a large result as one 88,566-character line from `structuredContent`, and as a 149,500-character line from the `content` path, neither of which Read's offset and limit can page ([claude-agent-sdk-typescript #187](https://github.com/anthropics/claude-agent-sdk-typescript/issues/187)), and one Claude Code user saw the model invent IDs that had fallen past a 2 KB preview rather than read the spill file ([claude-code #45770](https://github.com/anthropics/claude-code/issues/45770)). The 13 tools the catalog tags `code-output`, from `decompile_function` and `get_review_package` to `x64dbg_disasm` and the session-replay tools, should therefore share one budget of about 24,000 characters (about 9K tokens), below every client threshold and Claude Code's warning, with identifiers, totals and the continuation hint at the top; a hint like `showing 1-200 of 1834; next: offset=200` costs about 20 tokens ([hint and hexdump measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/scripts/measure2_out.txt)). Nine tools have no cap at all: `get_imports`, `get_memory_map`, `find_api_calls`, `detect_crypto`, `generate_iocs`, `batch_decompile`, `find_stack_strings` and the two session-replay tools; `find_stack_strings` returned 15.7K tokens on the synthetic cache, and its `ioc_only=True` mode did not shrink that ([measured outputs](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/measure_results.stdout)).

### Row format matters as much as row count

For uniform records, the cheapest formats on the proxy tokenizers are CSV, TSV and single-spaced text at **41-49% of pretty-printed JSON**, followed by compact Markdown tables at 44-52%, padded tables at 57-61%, minified JSON at 63-67% and YAML near 80% ([format measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/scripts/measure_out.txt)). TOON, a format built for exactly this purpose, came out no smaller than TSV on binary-mcp-shaped data (same source), and its accuracy case is contested: one independent tester "failed to find circumstances where TOON was the best-performing format" ([improvingagents, TOON benchmarks](https://www.improvingagents.com/blog/toon-benchmarks/)), and an agentic benchmark found it saved at most 18% of tokens at about a 9-point accuracy cost and broke parallel tool calls for most models ([Notation Matters](https://arxiv.org/abs/2605.29676)). binary-mcp's listings use the expensive end of the range. `get_functions` spends six Markdown lines and about 70 tokens per function, including a signature line that repeats the name ([server.py:2468](../src/server.py#L2468)), and the same 100 rows as TSV with signatures cost 53% less, or **84% less** with only address, name and call count ([what-if measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/whatif.json)). Strings drop 52-66% the same way, imports drop 70% when grouped per DLL (same source), and `scan_pseudocode` already has a summary mode 78% smaller than its default, 1,344 tokens against 6,133, that the model must know to ask for ([review_tools.py:469](../src/tools/review_tools.py#L469); [measured outputs](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/measure_results.stdout)).

### Reverse-engineering artifacts have cheaper encodings that lose nothing

RE output has its own costly habits, measured here on a real 108 KB MSVC launcher and 656 real Ghidra decompilations ([RE compaction measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/data/results.md)). o200k groups digits in threes and splits at hex letters, so a 64-bit `0x%016x` address averages **9.6 tokens against 3.8 for an image-relative RVA**, and the `0x` prefix alone costs about two ([RE compaction measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/data/results.md); [literal costs](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/data/literals.md)). Dropping the bytes column and printing RVAs cuts x64dbg-style disassembly from 28.0 to 12.4 tokens per instruction; grouping imports by DLL saves 76%; an adjacency list with RVAs cuts a 688-edge call graph by 67% against an edge list and by 87% against indented JSON; and a one-line register view with zero registers omitted saves 70% (same sources). Raw bytes show the widest spread: `hexdump -C` costs about 3 tokens per byte against about 1 for packed hex and 0.7-0.9 for base64, collapsing repeated lines the way `hexdump` does by default cut a mostly zero 4 KB region from 10,754 to 684 tokens, and a simulated 256-byte binary-mcp x64dbg read costs 927 tokens including its envelope, where plain hex would cost about 299 ([RE compaction measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/data/results.md); [hint and hexdump measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/scripts/measure2_out.txt); [what-if measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/whatif.json)). Pseudocode compresses less safely. Structure-preserving normalization cut the 656 functions by **23.3%**, most of it from shortening Ghidra auto-names such as `param_1` and `local_28` (13.3%), but those names encode stack offsets and addresses that renames and xref follow-ups rely on, and removing indentation saved 9.3% on o200k yet only 0.3% on Anthropic's older public tokenizer ([RE compaction measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/data/results.md)). No paper measures these transforms on RE tasks; the closest evidence, on ordinary source code, found that stripping formatting saved 24.5% of input tokens "with negligible" effect on performance ([The Hidden Cost of Readability](https://arxiv.org/html/2508.13666v1)). Peers fixed the worst RE-specific blowup the same way twice: ReVa and GhidrAssistMCP both stopped listing every `undefined` byte of a structure after one 304-byte struct cost about 11,000 tokens ([ReVa #202](https://github.com/cyberkaida/reverse-engineering-assistant/issues/202); [GhidrAssistMCP commit 1fc74f2](https://github.com/symgraph/GhidrAssistMCP/commit/1fc74f2d5584eeefb9c57a69eda12ceecdd1912d)). binary-mcp's own equivalent is its decompiler-caveat legend, which repeats a long fixed sentence per caveat for every function: 180 tokens for four caveats where a terse legend would cost about 47, and 2,098 summary tokens in one 50-function batch ([what-if measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/whatif.json); [decompiler_caveats.py:203](../src/utils/decompiler_caveats.py#L203)).

### The injection notice outweighs many of the results it wraps

Every untrusted body passes through `wrap_untrusted`, which adds a header, a 523-character notice, the body and a terminator ([formatters.py:152](../src/utils/formatters.py#L152)). The envelope costs **140-145 tokens, 109 of them the notice**; across the 86 measured calls, 69 envelopes cost 9,898 tokens, and on small results the envelope is most of the payload, 140 of 297 tokens for `check_binary` and 139 of 266 for `analyze_binary` on a warm cache, while `batch_decompile` repeats it for every function ([results summary](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/results_summary.json); [function_hash_tools.py:698](../src/tools/function_hash_tools.py#L698)). The defense research supports a cheaper split. Spotlighting, the technique this envelope resembles, cut attack success from about 50% to under 3% with datamarking in its authors' tests ([Hines et al., spotlighting](https://arxiv.org/abs/2403.14720)), and Microsoft's description of the technique puts the rule in the system prompt, telling the model "not to follow instructions in the untrusted content", and puts only "a specific randomized text delimiter" around the data ([MSRC](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)). A nonce-tagged marker with a one-line note costs about 29 tokens, while datamarking code would add 12-42% and base64 87-134% ([format measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/scripts/measure_out.txt)). Moving the notice into server instructions and keeping a one-line marker per response saves about 114 tokens per envelope, roughly 16K over a 100-call session at 1.5 wrapped blocks per call (this report's arithmetic). No study yet compares that split with a per-block notice on current frontier models, so it is a security decision as much as a token one.

Errors are the one category that is small, 11-125 tokens, but they are all returned with `isError: false`, and generic failures collapse to a 24-token "Reference ID ... Please contact support" line that names neither the problem nor a fix ([security.py:1104](../src/utils/security.py#L1104); [error measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/out/errors_summary.txt)). The specification says execution errors belong in results flagged `isError: true` with "actionable feedback that language models can use to self-correct and retry" ([MCP 2025-11-25 tools](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2025-11-25/server/tools.mdx)), and Anthropic advises against "opaque error codes or tracebacks" ([Anthropic, writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)). The cost of a vague error is the retry it provokes, which repeats a full round trip, not the error's own length.

## Peer RE servers converged on caps, profiles and triage-first calls

The most-used reverse-engineering servers share a common toolkit, and binary-mcp is missing several of its pieces. Paging defaults cluster at 100 items with hard caps: LaurieWired's GhidraMCP, the most-starred Ghidra server, defaults list tools to 100 items, caps pages at 2,000 and returns `hasMore` ([GhidraMCP server.py](https://github.com/LaurieWired/GhidraMCP/blob/1e980252087b2479a21b9ca6d82d5829538651a7/src/ghidra_mcp/server.py); [Page.java](https://github.com/LaurieWired/GhidraMCP/blob/1e980252087b2479a21b9ca6d82d5829538651a7/extension/src/main/java/com/lauriewired/ghidramcp/core/Page.java)), Binary Ninja's built-in server returns `count`, `total`, `nextOffset` and `truncated` ([Binary Ninja MCP guide](https://github.com/Vector35/binaryninja-api/blob/dev/docs/guide/mcp.md)), and radare2's r2mcp pages at 1,000 lines and lets list tools return only a count ([r2mcp.h](https://github.com/radareorg/radare2-mcp/blob/562c0cf23c42b65b3052f0b294d8778c20facbde/src/r2mcp.h); [r2mcp commit 097c9b0](https://github.com/radareorg/radare2-mcp/commit/097c9b0b67d7f89bc0a8702242b046a5e48c4c60)). Decompilation is bounded far more tightly than in binary-mcp. ReVa defaults to 50-line windows "to conserve context" ([ReVa DecompilerToolProvider.java](https://github.com/cyberkaida/reverse-engineering-assistant/blob/a05a6b0a18649efd6d74ec8447bdadf8d468c365/src/main/java/reva/tools/decompiler/DecompilerToolProvider.java)), and mrexodia's ida-pro-mcp, with about 13,000 stars, defaults decompiles to 500 lines and caps them at **30,000 characters, a quarter of binary-mcp's default**, behind a global 50,000-character output cap that returns a schema-preserving preview plus a download URL ([ida-pro-mcp api_analysis.py](https://github.com/mrexodia/ida-pro-mcp/blob/c133c3853faa111a9b00ee615c013b720d0c4acd/src/ida_pro_mcp/ida_mcp/api_analysis.py); [ida-pro-mcp rpc.py](https://github.com/mrexodia/ida-pro-mcp/blob/c133c3853faa111a9b00ee615c013b720d0c4acd/src/ida_pro_mcp/ida_mcp/rpc.py)). ida-pro-mcp also collapsed whitespace in pseudocode and disassembly and switched to compact JSON separators in a single optimization pass ([ida-pro-mcp commit 244d2d3](https://github.com/mrexodia/ida-pro-mcp/commit/244d2d3b665ebdb13ccb622110d665b778f72725)), and pyghidra-mcp cut its imports page from 100 to 25 after a context blowup ([pyghidra-mcp commit aa4c060](https://github.com/clearbluejar/pyghidra-mcp/commit/aa4c06023d25f57a51213ecdc7138e51a1874ad0)).

On tool surface, profiles and lazy loading are now standard. ida-pro-mcp ships `triage` (9 tools) and `readonly` (34) profiles and hides its debugger tools by default ([ida-pro-mcp triage profile](https://github.com/mrexodia/ida-pro-mcp/blob/c133c3853faa111a9b00ee615c013b720d0c4acd/profiles/triage.txt); [ida-pro-mcp README](https://github.com/mrexodia/ida-pro-mcp/blob/c133c3853faa111a9b00ee615c013b720d0c4acd/README.md)). bethington's 209-tool Ghidra server loads only its core groups on connect because "Advertising all 209 endpoints in a single `tools/list` is over a hard limit for at least one major provider" ([bethington README](https://github.com/bethington/ghidra-mcp/blob/cf8b12db27eb139b28b90eaa3488306da910d759/README.md)), and its own measurement concluded that discoverability, not raw token count, "is the real challenge" ([bethington Context-Window-Analysis.md](https://github.com/bethington/ghidra-mcp/blob/cf8b12db27eb139b28b90eaa3488306da910d759/docs/Context-Window-Analysis.md)). The only controlled cost measurement found comes from blacktop's Rust IDA server: its 28-tool `lean` profile cost **25% less than the 76-tool default** ($0.275 against $0.367), used 42 rather than 52 tool calls, recorded no tool errors against one, and saved "almost all" of that in cache-read tokens (849,325 down to 442,166), measured in Claude Code 2.1.288 with Sonnet 5.5 over three trials of three tasks ([ida-mcp-rs README](https://github.com/blacktop/ida-mcp-rs/blob/15d16aba427bedc8a23c7a54d8adee06d427b740/README.md)). The sample is small and the research did not establish whether tool search was active in that run, but it is direct evidence that a smaller surface cut cost without hurting correctness. At the far end, Hex-Rays' official server exposes six tools ([HexRaysSA/ida-mcp metadata snapshot](https://github.com/HexRaysSA/ida-mcp/blob/df6de7985b534a964c125d5a86e41b26b17b14f6/tests/snapshots/mcp_metadata.json)), and svnscha's WinDbg server makes do with 11 command-passthrough tools whose output is bounded at 2,000 lines and 64 KiB, plus a Claude Code plugin it says costs about 400 tokens of always-on context ([mcp-windbg debug_session.py](https://github.com/svnscha/mcp-windbg/blob/48e4350d57c44a38068be4f64e89a0fe60fe5c04/src/mcp_windbg/debug_session.py); [mcp-windbg CHANGELOG](https://github.com/svnscha/mcp-windbg/blob/48e4350d57c44a38068be4f64e89a0fe60fe5c04/CHANGELOG.md)).

Workflow conventions converge as well. ida-pro-mcp's `survey_binary` tells the model to "Use this as your FIRST tool call" and returns the top 15 strings and functions ranked by xref count along with imports by category, and its `analyze_function` caps pseudocode at 100 lines and strings at 10 ([ida-pro-mcp api_survey.py](https://github.com/mrexodia/ida-pro-mcp/blob/c133c3853faa111a9b00ee615c013b720d0c4acd/src/ida_pro_mcp/ida_mcp/api_survey.py); [ida-pro-mcp api_composite.py](https://github.com/mrexodia/ida-pro-mcp/blob/c133c3853faa111a9b00ee615c013b720d0c4acd/src/ida_pro_mcp/ida_mcp/api_composite.py)), while ReVa's triage skill counts strings before paging through them "100-200 strings at a time" ([ReVa binary-triage skill](https://github.com/cyberkaida/reverse-engineering-assistant/blob/a05a6b0a18649efd6d74ec8447bdadf8d468c365/ReVa/skills/binary-triage/SKILL.md)). The research systems work the same way: Microsoft's Project Ire summarizes key functions one at a time into a "chain of evidence" ([Microsoft Research, Project Ire](https://www.microsoft.com/en-us/research/blog/project-ire-autonomously-identifies-malware-at-scale/)), and Google found that chunking whole binaries "led to vague and non-specific outcomes", while noting that decompiled code is "five to 10 times more concise" than disassembly ([Google Cloud, Gemini for malware analysis](https://cloud.google.com/blog/topics/threat-intelligence/gemini-for-malware-analysis)). One peer pattern to avoid: mrphrazer's headless servers put a compact summary in `content` and the full payload in `structuredContent` ([binary-ninja-headless-mcp README](https://github.com/mrphrazer/binary-ninja-headless-mcp/blob/7fafd7523838fa2627a972869e34815fc461834f/README.md)), so on Claude Code, Codex and VS Code the model sees the full payload and never the summary.

Against that field, binary-mcp is ahead in places. Its x64dbg grouping matches the consolidation that bromoket's server advertises as "23 mega-tools" over "153 REST endpoints" ([bromoket x64dbg_mcp README](https://github.com/bromoket/x64dbg_mcp/blob/d8e6cac465128c18f63c51e5de55616d91c09bcf/README.md)), its `tools/list` is deterministic, its long analyses return a job handle after a 25-second inline deadline ([docs/jobs.md](../docs/jobs.md#L29)), and four tools already offer concise modes. It lacks what nearly every peer added after its first context blowups: server instructions, startup profiles, a decompile cap near peer levels, limits on imports and other bulk listings, and count-only modes.

Sequencing matters as much as the list. Rows 0 to 4 belong in one release, because row 0 gives the before-and-after numbers, rows 3 and 4 depend on each other, and only row 4 touches a security-sensitive test suite. The definition rewrite in row 7 should land before any tool is marked `alwaysLoad`, since an always-loaded tool pays its full description in every session. Each step should then be checked the way blacktop checked its lean profile: a fixed set of RE tasks run a few times per configuration in Claude Code, comparing cost, tool calls, tool errors and cache-read tokens ([ida-mcp-rs README](https://github.com/blacktop/ida-mcp-rs/blob/15d16aba427bedc8a23c7a54d8adee06d427b740/README.md)), so that a cheaper server is also shown not to be a less accurate one.

Several popular ideas should stay out. Runtime toggling of tool groups with `list_changed` invalidates the prompt cache in every client that loads tools upfront, is only partly honoured by Cursor, and was dropped from GitHub's own server ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching); [Cursor forum](https://forum.cursor.com/t/doubts-regarding-the-capabalities-negotiations/147888/2)). A server-side search-and-invoke facade, including FastMCP 3.1's BM25 search transform, belongs at most behind an opt-in profile for clients without deferral, because it duplicates Claude Code's built-in search, erases per-tool permissions and hooks, and by default returns full JSON definitions from each search ([FastMCP tool search docs](https://gofastmcp.com/servers/transforms/tool-search)). An `execute_python`-style tool would place model-written code beside malware-authored strings, the code-injection path that the programmatic tool calling documentation warns about ([Claude programmatic tool calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)), and MCP sampling is deprecated and gone from FastMCP 4 ([FastMCP changelog](https://gofastmcp.com/changelog)). Smaller refusals follow from the measurements: TOON is no smaller than TSV here; a rendered call graph costs up to 4,784 image tokens on current Claude models ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)) where a 35-node text tree cost 546 ([format measurements](../research_notes/Binary%20MCP%20token%20efficiency/artifacts/scripts/measure_out.txt)); datamarking or base64-encoding code costs 12-134% more; stripping `_meta._fastmcp.tags` saves 2.5K wire tokens that probably never reach the model while breaking [test_tool_catalog.py:125](../tests/test_tool_catalog.py#L125); and raising `anthropic/maxResultSizeChars` would only keep more tokens resident.

## Conclusion

The surprise in this audit is how much of binary-mcp's cost comes from defaults it never chose. FastMCP's verbatim docstrings make up most of the tool list, and its automatic wrapping of string results doubles every response on the wire and, on the clients that prefer `structuredContent`, swaps the Markdown the server formats so carefully for an escaped JSON string; neither shows up in code review, because neither is written anywhere in binary-mcp. Budgets follow the same pattern. The 120,000-character decompile default reflects what the server can produce, while the effective ceiling is set by the strictest client, around 40,000 characters or 10,000 tokens, above which clients cut blindly and the server's own continuation hints, placed at the end, are the first thing lost. Setting budgets from client limits downward, with handles and hints at the top of every response, turns truncation from an accident into part of the protocol.

Tool search has also changed what a description is for. In Claude Code, description length now costs little until a tool is found, but description text decides whether it is found at all, so the rewrite should spend the first sentence and the first 4,096 characters on the words an analyst would search for rather than simply minimizing length, while startup profiles serve the clients that still pay for every byte. The single most repeated text in binary-mcp's results is its prompt-injection notice, and the spotlighting research puts that rule in the system prompt, exactly where token efficiency wants it; the convergence is promising but untested on current models, so it should ship as a reviewed security change rather than a formatting tweak. And because the repository already enforces its house style on dash characters with a test, token budgets deserve the same treatment: the contributor template that produced today's bloat will reproduce it one tool at a time unless continuous integration says otherwise.
