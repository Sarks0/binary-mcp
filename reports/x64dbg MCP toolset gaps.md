# Repair, then extend, binary-mcp's x64dbg surface

The fastest way to make binary-mcp's x64dbg tooling useful to an LLM is to fix what is broken before adding anything new. **Sixteen of roughly 175 ops always fail.** Four more quietly do something other than what they report, for example a hardware breakpoint that is always set to execute while the tool says it set the requested type. `session.status` also reports "paused" while the target is running (binary-mcp code audit). Once those are fixed, the biggest gain comes from **non-breaking logging breakpoints with fast resume**. x64dbg already supports them natively, and they turn dozens of pause, inspect and resume round trips into one call. They underpin API monitoring, unpacking, config extraction and anti-debug attribution ([ConditionalBreakpoint.md](https://github.com/x64dbg/docs/blob/master/introduction/ConditionalBreakpoint.md)). The next tier is a set of cheap, read-only `DbgFunctions()` wrappers (call stacks, SEH chain, named handles, TCP connections, patches, page rights), which the plugin does not use at all today ([_dbgfunctions.h](https://github.com/x64dbg/x64dbg/blob/development/src/dbg/_dbgfunctions.h)). After that come composite workflow tools for unpacking, injection and behaviour profiling. On interface design, binary-mcp's 16 grouped tools already meet vendor tool-count guidance. However, its op catalogue lists argument names without types, required flags or enums, so argument errors stay invisible to the model. Typed schemas and input examples raised complex-parameter accuracy from 72% to 90% in Anthropic's testing ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). binary-mcp's security posture is already ahead of most competitors: it never launches a sample, and raw commands pass through fail-closed allowlists. The remaining hole is on the output side, because strings from the sample are a demonstrated prompt-injection channel ([arXiv 2605.30677](https://arxiv.org/html/2605.30677)).

## Twenty broken or misleading ops come first

Agents in debugger studies recover from failures only when the tool states a specific cause. Big Sleep's agent recovered after a run failure named the missing module ([Project Zero](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html)). binary-mcp's broken ops do the opposite. **Sixteen ops call HTTP endpoints that obsidian_server never routes and that have no plugin handler.** These are `session.attach/detach/minidump`, six exception and conditional breakpoint ops, `breakpoint.get_logs`, `trace.log_api_params`, and the bookmark and function annotation ops. **Four more succeed silently while doing the wrong thing.** `breakpoint.set_hardware` always sets an execute breakpoint because the bridge sends `type` and the plugin reads `bp_type`. `set_memory` always sets an access breakpoint. `context.stack` ignores its depth argument and `execution.skip` ignores its count (binary-mcp code audit). Silent mismatches are worse than outright failures, because the model believes it armed a write watchpoint and then reasons from an event that never fires.

The broken set is not peripheral. The malware-workflow research rates **conditional and log-only breakpoints, and exception breakpoints with pass or swallow policy, as P0**: unpacking, API monitoring, anti-debug, config extraction and shellcode analysis are blocked without them ([x64dbg help](https://help.x64dbg.com/en/latest/introduction/ConditionalBreakpoint.html); [Check Point anti-debug](https://anti-debug.checkpoint.com/)). Every one of these ops maps onto a registered x64dbg command or SDK call, so the fixes are plumbing rather than research.

## Logging breakpoints and read-only SDK wrappers deliver the most value per line of code

The highest-leverage addition is to expose x64dbg's own conditional breakpoint machinery properly. On every hit x64dbg increments `$breakpointcounter` and evaluates a break condition. With fast resume and a zero condition it resumes immediately, without plugin callbacks or GUI updates, after printing log text in a rich format language ([ConditionalBreakpoint.md](https://github.com/x64dbg/docs/blob/master/introduction/ConditionalBreakpoint.md)). That language decodes **UTF-16 strings, Win32 errors, NTSTATUS codes, memory blocks, disassembly and module names** inline, for example `{utf16@[esp+4]}` or `{winerror@eax}` ([Formatting.md](https://github.com/x64dbg/docs/blob/master/introduction/Formatting.md)). Practitioners build API monitors and unpacking hunts on exactly this pattern ([n1ght-w0lf](https://n1ght-w0lf.github.io/tutorials/writing-x64dbg-scripts)). Competitors expose it as SetConditionalBreakpoint and SetBreakpointFastResume ([duty1g](https://github.com/duty1g/x64dbg-mcp-server)), and as paged breakpoint-log files read without stopping the debuggee ([DNLINYJ](https://github.com/DNLINYJ/better-x64dbg-mcp)). The safety boundary is clear. Log text can call only expression functions, all read-only except `arg.set`. **`bpcommand` runs an arbitrary debugger command, so it could carry `loadlib` or `scriptdll`**, and `SetBreakpointLogFile` writes files ([x64dbg_capabilities research, citing x64dbg.cpp](https://github.com/x64dbg/x64dbg/blob/development/src/dbg/x64dbg.cpp)). Microsoft's WinDbg MCP documentation warns about the same indirect-execution route through breakpoint commands ([MS Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/windbg-mcp-overview)).

The second cluster is structured state the plugin already has access to but never reads. The plugin registers lifecycle callbacks and uses only `Script::Module`. **It never calls `DbgFunctions()`** ([x64dbg_capabilities research](https://github.com/x64dbg/x64dbg/blob/development/src/dbg/_dbgfunctions.h)). The reads below have no side effects and recur across competing servers: handles and TCP connections in Wasdubya and Akhil, and SEH chain and PEB in duty1g ([Wasdubya](https://github.com/Wasdubya/x64dbgMCP); [Akhil](https://github.com/Akhil-Chaturvedi/x64dbg-MCP); [duty1g](https://github.com/duty1g/x64dbg-mcp-server)).

## Composite tools turn analyst loops into single calls

Practitioners agree that raw step-and-read calls are expensive and that the payoff lies in "run region X and tell me what changed". G DATA found x64dbg MCP to be **the most token-hungry tool in the lab**, at about €5-20 of API cost per sample ([G DATA](https://blog.gdatasoftware.com/2026/03/38381-llm-malware-analysis)). x64.ooo found snapshot/diff and trace analysis more productive than raw MCP calls on resistant binaries ([x64.ooo](https://x64.ooo/posts/2026-02-12-cooking-with-x64dbg-and-mcp/)). The agent research points the same way. EnIGMA's interactive tools cut turns to solve from 14.9 to 11.5, and a demonstrations-free variant dropped from 29.5% to 23.3% solved ([arXiv 2409.16165](https://arxiv.org/html/2409.16165)). KnifeCoat's Frida work found that agents skip steps in multi-step setup and leak suspended processes. It argues for **atomic server-side composites** ([KnifeCoat](https://knifecoat.com/Posts/Scalable+research+tooling+for+agent+systems)). Each composite below automates a loop that analysts describe doing by hand, and each is built on the Tier 0 and Tier 1 primitives.

**API capture on entry and exit** is the keystone. Varonis breaks on VirtualAlloc's *return*, not its entry, because the analyst wants the allocated address and later the bytes written to it ([Varonis](https://www.varonis.com/blog/x64dbg-unpack-malware)). Config extraction likewise needs the output buffer after CryptDecrypt returns ([Crovax](https://medium.com/@crovax/extracting-hancitors-configuration-with-ghidra-7963900494b5)). binary-mcp decodes parameters at entry and has `run_until_return`, but no single call captures both sides. **Unpacking** needs a Scylla-equivalent. Scylla.dll exports headless `ScyllaIatSearch`, `ScyllaIatFixAutoW`, `ScyllaDumpProcessW` and `ScyllaRebuildFileW`, while x64dbg itself only starts Scylla's GUI ([FunctionExport.h](https://github.com/NtQuery/Scylla/blob/master/Scylla/FunctionExport.h); [cmd-plugins.cpp](https://github.com/x64dbg/x64dbg/blob/development/src/dbg/commands/cmd-plugins.cpp)). The bridge currently blocklists `scylla`, so headless Scylla would be a deliberate, path-pinned exception. The alternative is a pure-Python IAT rebuild from memory reads. **Injection** follows well-documented API chains: hollowing is CreateProcess(CREATE_SUSPENDED), NtUnmapViewOfSection, VirtualAllocEx, WriteProcessMemory, SetThreadContext, ResumeThread ([Elastic](https://www.elastic.co/blog/ten-process-injection-techniques-technical-survey-common-and-trending-process)). OALabs unpacks such samples "with a single breakpoint on WriteProcessMemory" ([OALabs](https://castbox.fm/channel/OALabs-id2238270)). Because x64dbg has no confirmed child-follow mode, the realistic handoff is to stop before ResumeThread, report the PID and injected entry point, keep the child suspended and attach a second session ([x64dbg FAQ](https://github.com/x64dbg/x64dbg/wiki/Frequently-Asked-Questions); [DbgChild](https://github.imc.re/therealdreg/DbgChild)).

## Typed schemas and truthful state matter more than tool count

binary-mcp's grouping is sound on count: 16 tools and about 7.4k tokens sit under Anthropic's 10K-token tool-search threshold and OpenAI's soft limit of about 20 functions ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use); [OpenAI](https://developers.openai.com/api/docs/guides/function-calling)). The weakness is *inside* each group. A string `op` with argument names but no types moves the selection problem into a parameter the model must guess. Benchmarks locate most MCP errors exactly there, in wrong-tool selection and parameter mistakes ([MCP-Atlas](https://arxiv.org/html/2602.00933v1)). Strict enums "prevent invalid states" ([OpenAI](https://developers.openai.com/api/docs/guides/function-calling)). No published A/B study compares one `op`-discriminated tool with N separate tools, so binary-mcp has to measure this with its own evals.

The snapshot in D2 also addresses a subtler failure. EnIGMA's Claude agent "soliloquised", inventing tool observations, in 10-48% of trajectories, and those runs succeeded about 26% less often ([arXiv 2409.16165](https://arxiv.org/html/2409.16165)). Results that state plainly "no event; target still running" with a `state_version` give the model less room to invent state.

## Keep the no-launch line and harden the output channel

binary-mcp's refusal to launch samples is the minority position among x64dbg servers: duty1g, rison1337 and x64dbg-automate all launch targets. It matches **Microsoft's WinDbg MCP secure mode, which blocks process launch and `.shell` by default** ([MS Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/windbg-mcp-overview)). It also removes one leg of the "lethal trifecta", so long as no network-capable tool is added ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). duty1g's history shows what laxer defaults cost. A write-up assigns it a CVE for exposing every tool unauthenticated on 0.0.0.0 before v1.1, although the advisory sources disagree on the affected versions ([ThreatFrontier](https://threatfrontier.com/articles/x64dbg-mcp-server-cve-2026-107824-unauthenticated-debugger)).

The commands that should stay blocked fall into seven groups ([x64dbg.cpp](https://github.com/x64dbg/x64dbg/blob/development/src/dbg/x64dbg.cpp)). Commands that load or run code in the debugger: `loadlib`, `freelib`, `scriptdll`, `script*` and `plug*`. Commands that run code in the debuggee: `createthread`. Commands that start or restart processes: `init` and `restartadmin`. Commands that change system or debugger configuration: `setjit`, `chd`, `settingset` and `config`. Commands that write files to arbitrary paths: `SaveLog`, `RedirectLog`, `dbsave`, `Set*BreakpointLogFile` and `TraceSetLogFile`. Commands that execute arbitrary debugger commands: `Set*BreakpointCommand` and `TraceSetCommand`. Commands that are destructive to the debuggee: `handleclose` and `killthread`. `symdownload` makes network requests and should stay off by default. File-writing features that this report recommends (minidump, `PatchFile`, trace recording, Scylla dumps) are safe only if the plugin chooses the path inside binary-mcp's output directory and caps the size. ScyllaHide control is a reasonable opt-in, but it injects a hook DLL into the debuggee. rison1337 disables NtContinueHook and KillAntiAttach after reproducing a crash ([rison1337](https://github.com/rison1337/x64dbgMCP); [scylla_hide.ini](https://github.com/x64dbg/ScyllaHide/blob/master/ConfigCollection/scylla_hide.ini)). Kernel hiders such as TitanHide and HyperHide require PatchGuard and DSE to be disabled, so they belong in lab setup documentation, not MCP tools ([TitanHide](https://github.com/mrexodia/TitanHide); [HyperHide](https://github.com/Air14/HyperHide)).

The open risk is **output-borne prompt injection**. Crawford and McClure compiled payloads into binaries that reached the model through `list_strings` and decompiler output, using fake chat-template tokens such as `<|im_start|>`. Swapping angle brackets for square brackets cut attack success from 100% to 40% on Qwen3-8B. Regex detection reached only **0.6 recall**, against 1.0 for a small neural classifier, and non-printing bytes defeated strings extraction entirely ([arXiv 2605.30677](https://arxiv.org/html/2605.30677)). Their model was small, and no measurement against frontier models in an RE setting exists yet. x64dbg exposes the same channels: strings, labels and comments, ASCII-rendered memory, module and export names, ODS text and `bplog` output. binary-mcp already fences sample-derived text. It should also keep that text in dedicated `untrusted` fields, neutralise chat-template tokens and fence-closing sequences, escape non-printing bytes, cap lengths, and never echo sample text inside error messages. Microsoft's XPIA classifier, which runs over MCP sampling, and glslang's redacted JSONL transcripts are the reference designs for an optional classifier and an audit trail ([MS Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/windbg-mcp-overview); [glslang](https://github.com/glslang/windbg-mcp)). A per-call audit log is effort S and should ship with Phase 1.

## A four-phase roadmap

**Phase 0, about two weeks, correctness.** Ship F1-F10, add a read-back regression test for every op, and make `session.status` live. Nothing new should be built on ops that currently lie. **Phase 1, about four to six weeks, cheap leverage.** Add log breakpoints and log reading (T1.1-T1.2), then the read-only `DbgFunctions()` wrappers (T1.3-T1.9) with a version probe, then the allowlist additions and `int_convert`/telescope (T1.10-T1.11). In parallel, do the design work that makes these usable: typed `oneOf` schemas (D1), the context snapshot (D2), structured output (D3), the error taxonomy (D4), output-hygiene hardening and an audit log. Build the eval harness (D9) here so later phases are measured against a baseline. **Phase 2, about six to eight weeks, workflow composites.** Build `run_until` with attribution (T2.1), entry/exit API capture (T2.2), anti-analysis detection with force-return (T2.4), TLS callbacks (T2.10), hash resolution (T2.9), then `profile_behavior` (T2.3). Alongside them, add response budgeting, the read/write split with a default-off write gate, and progressive disclosure (D5-D7) as the surface grows. **Phase 3, a quarter, heavy features.** Build unpack-and-rebuild with headless Scylla or a Python IAT rebuild (T2.5), injection monitoring with child hold and multi-session attach (T2.6), trace recording with an offline query engine (T2.7), the implant scanner (T2.8) and gated `invoke_function` (T2.11). Effort sizes are this report's engineering judgement (S under a day or two, M about a week, L multi-week), not figures from the sources.

## Conclusion

The research changes where the effort should go. binary-mcp does not need more ops. It needs its existing ops to be *truthful* and its new ops to be *workflow-shaped*. x64dbg already contains most of what an LLM analyst lacks, including non-breaking log breakpoints, a rich format language, call stacks, handles, patches and a documented trace format. The plugin has never called into most of it. That makes the highest-return work integration rather than invention, and it means binary-mcp can close most of the functional gap with rison1337 and duty1g without adopting their launch-capable, code-loading surfaces.

The second implication concerns safety. As binary-mcp adds logging breakpoints, ODS capture and behaviour profiles, it will feed the model far more attacker-controlled text than it does today. Input-side allowlists stay necessary but are no longer sufficient, so output hygiene must harden in step with each new read path rather than afterwards. Some questions remain open and should be settled in Phase 1 evals: whether grouped `op` tools with typed `oneOf` schemas perform as well as split tools, how much log volume a behaviour profile generates, and whether the targeted x64dbg build carries the newer `DbgFunctions` members.
