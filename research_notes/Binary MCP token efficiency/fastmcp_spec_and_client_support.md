## Q1. FastMCP 2.x: exposing tool subsets (`include_tags`/`exclude_tags`) and changing the tool list at runtime (enable/disable plus `notifications/tools/list_changed`)

### Takeaway
In 2.x (≥2.8.0), `FastMCP(include_tags=..., exclude_tags=...)` hard-filters tools at construction. Tag-excluded tools are neither listed nor callable. `tool.disable()`/`tool.enable()` change the list at runtime, and since 2.9.1 FastMCP automatically emits `notifications/tools/list_changed`. Both are **server-global**. There are no per-session lists in 2.x unless you write middleware.

### Cited Findings
- **2.8.0 ("Transform and Roll Out", dated 2024-06-10 in the changelog but really 2025-06-10; see Q6 for the date typo)** added "tag-based component filtering" (PR #748) and "Support enable/disable for all FastMCP components (tools, prompts, resources, templates)" (PR #781). The release notes say tag filtering lets you "selectively enable or disable tools, resources…" — [FastMCP changelog](https://gofastmcp.com/changelog) ([source mdx](https://github.com/PrefectHQ/fastmcp/blob/main/docs/changelog.mdx))
- 2.14.7 `FastMCP.__init__` accepts `include_tags: Collection[str] | None`, `exclude_tags: Collection[str] | None`, `tools=`, `tool_transformations: Mapping[str, ToolTransformConfig]`, `tool_serializer`, `include_fastmcp_meta`, `middleware=` and `instructions=`. Verified (source) — [server.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/server.py)
- Verified (test, 2.14.7): `include_tags={"category:static"}` listed only the static tool, and `exclude_tags={"code-output"}` removed every tool carrying that tag. A call to a tag-excluded tool returned `isError: true` with "Unknown tool: secret", so **exclusion also blocks calls** — [server.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/server.py)
- 2.14.7 `settings.py` also defines `include_tags`, `exclude_tags` and `include_fastmcp_meta` settings. The 3.0.0 changelog removes them as "unused include_tags/exclude_tags settings", so environment-variable control was apparently never wired up — [settings.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/settings.py); [FastMCP changelog v3.0.0](https://gofastmcp.com/changelog)
- **2.9.1 ("Call Me Maybe", 2025-06-26)**: "introduces automatic MCP list change notifications, allowing servers to notify clients when tools, resources, or prompts are dynamically updated" (PR #939) — [FastMCP changelog](https://gofastmcp.com/changelog)
- Verified (test, 2.14.7): the server advertises `capabilities.tools.listChanged = true`. Calling `tool.disable()` inside a tool call queued `notifications/tools/list_changed`, which the client received, and the next `tools/list` omitted the tool. Mechanism: `Tool.enable()`/`disable()` call `context._queue_tool_list_changed()`, and `Context` flushes the queue at request end. `ctx.send_tool_list_changed()` is also public — [tool.py @ v2.14.7 (line ~155)](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py); [context.py @ v2.14.7 (lines 518, 999-1023)](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/context.py)
- Every 2.x tool listing carries `"_meta": {"_fastmcp": {"tags": [...]}}`, which was 58 bytes for two tags in my test. `include_fastmcp_meta=False` removes that key and leaves custom `meta=` keys in place. Verified (test) — [server.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/server.py)

### Inferences
- For stdio (one client per process), global enable/disable is effectively per-client, so a "load category" meta-tool that calls `.enable()` on a tag group works in 2.x. Over HTTP with several clients, the change would leak to every connected client.
- The safest way to expose subsets in 2.x is a startup profile: a CLI flag or env var read by binary-mcp, mapped to `include_tags`/`exclude_tags` over the existing `category:<name>` tags. It needs no client support, and hidden tools cannot be called by mistake.
- Turning off `include_fastmcp_meta` saves roughly 8.5 KB of wire bytes per `tools/list` at 147 tools × ~58 bytes. It would also break binary-mcp's `tool_catalog.py`, which reads `_meta._fastmcp.tags`. Whether any client feeds `_meta` to the model is unverified; it is most likely wire-only.

### Gaps
- I did not test the combined semantics of `include_tags` and `exclude_tags` (which wins) on 2.14.7. The 3.x docs model this as blocklist plus `only=True` allowlist.

## Q2. FastMCP 2.x middleware: filtering tools (`on_list_tools`), post-processing results (`on_call_tool`), and built-in caching or size-limiting middleware

### Takeaway
Middleware (≥2.9.0) can filter `tools/list` and rewrite `tools/call` results (truncation, compaction, stripping `structuredContent`). Tools hidden by middleware stay **callable**. Truncating a tool that has an `outputSchema` breaks output validation unless you also handle `structured_content`. 2.x ships `ResponseCachingMiddleware` (2.13.0) but **no response-size-limiting middleware**; that arrived in 3.0.

### Cited Findings
- **2.9.0 ("Stuck in the Middleware With You", 2025-06-23)** "introduces … MCP Middleware" (PR #870). The middleware docs carry a `VersionBadge 2.9.0` — [FastMCP changelog](https://gofastmcp.com/changelog); [Middleware docs](https://gofastmcp.com/servers/middleware)
- Built-in middleware modules in 2.14.7: `caching.py`, `error_handling.py`, `logging.py`, `rate_limiting.py`, `timing.py` and `tool_injection.py` (`ToolInjectionMiddleware`, `PromptToolMiddleware`, `ResourceToolMiddleware`). There is no response-limiting module. Verified (directory listing) — [middleware/ @ v2.14.7](https://github.com/PrefectHQ/fastmcp/tree/v2.14.7/src/fastmcp/server/middleware)
- Verified (test, 2.14.7): `on_list_tools` receives FastMCP `Tool` objects that carry `.tags`, and returning a filtered list hides tools from `tools/list`. A tool hidden this way **remained callable** by name (the call returned "ok"). The low-level SDK only logs "Tool 'annotated' not listed, no validation will be performed" — [middleware docs](https://gofastmcp.com/servers/middleware)
- Verified (test, 2.14.7 with mcp 1.30.0): in `on_call_tool` you can edit `result.content[i].text` (truncation). Setting `result.structured_content = None` on a tool that **has** an `outputSchema` made the call fail with the content "Output validation error: outputSchema defined but no structured output returned". That message comes from the MCP SDK low-level server, which validates against the cached tool definition — [mcp python-sdk lowlevel server](https://github.com/modelcontextprotocol/python-sdk/blob/v1.30.0/src/mcp/server/lowlevel/server.py)
- Verified (test, 2.14.7): a middleware that returns `t.model_copy(update={"output_schema": None})` in `on_list_tools` and sets `structured_content=None` in `on_call_tool` works without validation errors. For a 10,837-byte Markdown result, the `tools/call` result fell from **22,974 bytes to 11,499 bytes** on the wire, and the tool definition from 465 to 265 bytes — [tool.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py)
- **`ResponseCachingMiddleware` (2.13.0, 2025-10-25)**: "Cache tool and resource responses with configurable TTLs". Its 2.14.7 signature is `ResponseCachingMiddleware(cache_storage=None, list_tools_settings=..., list_resources_settings=..., list_prompts_settings=..., read_resource_settings=..., get_prompt_settings=..., call_tool_settings=CallToolSettings(ttl, enabled, included_tools, excluded_tools), max_item_size=1MB)`, with a default TTL of 300 s. It caches `tools/call`, `resources/read`, `prompts/get` and the list methods — [FastMCP changelog v2.13.0](https://gofastmcp.com/changelog); [caching.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/middleware/caching.py); [middleware docs](https://gofastmcp.com/servers/middleware)
- The caching middleware returns "no-op objects" from the cache, so it "may not be compatible with other middleware that expects original subclasses". 3.3.0 (2026-05-15) partitioned the cache by access token, and 4.0.0 stopped caching error results — [caching.py docstring @ v3.4.9](https://github.com/PrefectHQ/fastmcp/blob/v3.4.9/src/fastmcp/server/middleware/caching.py); [FastMCP changelog](https://gofastmcp.com/changelog)

### Inferences
- Server-side caching saves backend compute (Ghidra or x64dbg re-runs) but **not model tokens**: a cached result is still delivered to the model in full. Token savings come from returning less, or from returning a handle or summary instead of repeating content.
- For binary-mcp on 2.x, a custom `on_call_tool` truncation or compaction middleware is straightforward to write. It must either run on tools without an output schema, or rewrite `structured_content["result"]` consistently. The simplest pattern is to strip output schemas globally (see Q4) and then truncate only the text.
- Middleware-hidden tools stay callable, so middleware filtering is a context-saving device, not an access control. Use `exclude_tags` (2.x) or visibility (3.x) when hiding must also block calls.

### Gaps
- I did not test middleware ordering interactions, for example a caching middleware placed before or after a truncation middleware.

## Q3. FastMCP 2.x Tool Transformation (`Tool.from_tool`, `ArgTransform`), composition and mounting with prefixes, and server `instructions`

### Takeaway
`Tool.from_tool` (≥2.8.0) can rename a tool, rewrite its description, and rename or hide arguments (a hidden argument needs a default). That makes it a good way to ship terse model-facing variants. In 2.14.7, `output_schema=None` on a transformed tool does **not** stop the parent's `structuredContent` from being forwarded. `mount(prefix=...)` adds `<prefix>_` to every tool name, and `instructions=` reaches the client in `InitializeResult`.

### Cited Findings
- 2.8.0 introduced "First-class tool transformation" (PR #745), which "lets you create enhanced variations of existing tools. You can now easily rename argumen[ts]…". 2.11.0 added "meta support to tool transformation utilities" and fixed "prune hidden parameter defs"; 2.11.3 "Ensure transformed tools generate structured content"; 2.13.2 "Prevent `$defs` mutation during tool transforms" — [FastMCP changelog](https://gofastmcp.com/changelog); [Tool transformation docs](https://gofastmcp.com/servers/transforms/tool-transformation)
- Verified (test, 2.14.7): `Tool.from_tool(base, name="dis", description="Disassemble.", transform_args={"count": ArgTransform(hide=True, default=5), "addr": ArgTransform(name="a", description="addr")}, output_schema=None)` produced `{"name":"dis","description":"Disassemble.","inputSchema":{"type":"object","properties":{"a":{"type":"integer","description":"addr"}},"required":["a"]}}`. The hidden argument vanished from the schema and the listing had no `outputSchema`. However, **the call still returned `structuredContent: {"result": ...}`** — [tool_transform.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool_transform.py)
- 2.14.7 also accepts a declarative `FastMCP(tool_transformations={name: ToolTransformConfig(...)})` mapping. Verified (signature only) — [server.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/server.py)
- Verified (test, 2.14.7): `parent.mount(child, prefix="ghidra")` exposes the child's `disasm` as **`ghidra_disasm`**. In 3.0 the parameter was renamed: "`mount(prefix="x") -> mount(namespace="x")`" — [Upgrading from FastMCP 2](https://gofastmcp.com/getting-started/upgrading/from-fastmcp-2); [Composition docs](https://gofastmcp.com/servers/composition)
- Verified (test, 2.14.7): `FastMCP("t", instructions="...")` is returned as `InitializeResult.instructions` — [server.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/server/server.py)
- Claude Code: "the server instructions field becomes more useful with tool search enabled. Server instructions help Claude understand when to search for your tools". Server instructions and upfront tool descriptions are cut at **4,096 characters**, and descriptions loaded through tool search at **16,384 characters**. Before v2.1.296 the shorter limit was 2,048 characters — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Claude Code omits any MCP tool whose full name (`mcp__<server>__<tool>`) exceeds **128 characters**. Gemini CLI truncates names "longer than 63 characters … with middle replacement" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp); [Gemini CLI MCP docs](https://github.com/google-gemini/gemini-cli/blob/main/docs/tools/mcp-server.md)

### Inferences
- Prefixing via mount costs `len(prefix)+1` characters per tool name, repeated in every listing and every call. Clients such as Claude Code already namespace names as `mcp__binary-mcp__<tool>`, so a server-side prefix is mostly redundant for a single server. Use it only if binary-mcp is split into mounted sub-servers whose names would collide.
- binary-mcp currently sends **no** `instructions`. In Claude Code, where tool search is on by default, a concise instructions block (well under 4,096 characters) that names the categories and when to search for them is cheap and directly improves discovery.
- To get terse variants without the duplicated payload in 2.x, combine `from_tool` with a result-stripping middleware (Q2), or put `output_schema=None` on the base tool itself.

### Gaps
- I did not verify which 2.x minor introduced the `tool_transformations=` constructor mapping.

## Q4. FastMCP output schema and structured content: how `-> str` tools serialize, and how to control it (`output_schema=None`, `ToolResult`)

### Takeaway
Yes. In 2.10.0 and later, including 2.14.7, 3.4.9 and 4.1.1, a tool annotated `-> str` gets an auto-generated wrapper `outputSchema` (`{"properties":{"result":{"type":"string"}},…,"x-fastmcp-wrap-result":true}`). Every call returns the Markdown **twice**: once in `content[0].text` and once as `structuredContent: {"result": "<same text>"}`. `output_schema=None` per tool, or a global strip middleware, removes both the schema and the duplicate. This matters because several major clients feed `structuredContent` to the model **instead of** the text (see Q9).

### Cited Findings
- **2.10.0 (2025-07-01)** "brings full compliance with the 6/18/2025 MCP spec update, introducing … output schemas for structured tool responses" ("MCP 6/18/25: Add output schema to tools"; "Add title field support to FastMCP components") — [FastMCP changelog](https://gofastmcp.com/changelog)
- FastMCP docs, Automatic Structured Content Rules: "Object-like results (dict, Pydantic models, dataclasses) → Always become structured content (even without output schema)"; "Non-object results (int, str, list) → Only become structured content if there's an output schema"; "All results → Always become traditional content blocks for backward compatibility". A return annotation is what generates the schema: "Without a type annotation, the tool only produces content" — [Tools docs](https://gofastmcp.com/servers/tools)
- Source (2.14.7): `ParsedFunction.from_function(..., wrap_non_object_output_schema=True)` wraps any non-object return schema and sets `output_schema["x-fastmcp-wrap-result"] = True`, then calls `compress_schema(output_schema, prune_titles=True, dereference=True)`. At call time, `structured_content={"result": result} if wrap_result else result` — [tool.py @ v2.14.7 (lines ~412-416, 554-564)](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py)
- Verified (test, 2.14.7): `def disasm(addr: int, count: int = 10) -> str` was listed with `"outputSchema": {"description": "Generic wrapper for non-object return types.", "properties": {"result": {"type": "string"}}, "required": ["result"], "type": "object", "x-fastmcp-wrap-result": true}` (**182 bytes**). The call returned `content=[{"type":"text","text":"# listing\n…"}]` **and** `structuredContent={"result": "# listing\n…"}` — [tool.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py)
- Verified (test): the same wrapper and duplication appear in **3.4.9** and **4.1.1**. In 3.4.9 the `description` key was gone from the wrapper (pydantic leak fixed in 3.2.4), and 3.2.0 also propagates `x-fastmcp-wrap-result` in the result `_meta` — [FastMCP changelog v3.2.0, v3.2.4](https://gofastmcp.com/changelog)
- Verified (test, 2.14.7): `@tool(output_schema=None)` on a `-> str` tool gives no `outputSchema` in the listing and `structuredContent=None` on the call. `-> dict` gives `outputSchema={"additionalProperties": true, "type": "object"}`, `structuredContent={...}` and compact JSON text. Returning `ToolResult(content=[TextContent(...)], structured_content={...})` gives **no** auto `outputSchema` and passes both parts through exactly as given — [tool.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py); [Tools docs, custom serialization](https://gofastmcp.com/servers/tools)
- 2.12.0 "restore output_schema=False compatibility" (an older spelling); 3.2.0 "suppress output schema for ToolResult subclass annotations"; 4.0.3 "don't infer an output schema for unconstrained sequences" — [FastMCP changelog](https://gofastmcp.com/changelog)
- There is no server-wide switch in 2.14.7 to disable auto output schemas; `settings.py` has no `output_schema` setting. Verified (grep) — [settings.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/settings.py)
- The spec rule FastMCP follows: "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block." This wording appears in both 2025-06-18 and 2026-07-28 — [Tools spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools); [Tools spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Measured: a 10,837-byte Markdown table (201 newlines, 400 double quotes) becomes 11,452 bytes as `json.dumps({"result": md})`, an increase of **5.7%** from JSON-escaping. That escaped form is what Codex, VS Code and (reportedly) Claude Code put in front of the model, per Q9. Verified (local script `t2b.py`) — [Codex models.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/models.rs)

### Inferences
- For binary-mcp (147 `-> str` tools, no `output_schema`), the current state is about 26.7 KB of `outputSchema` per `tools/list` (147 × 182 bytes) and **doubled wire size on every call**. On structuredContent-preferring clients the model sees JSON-escaped Markdown wrapped in `{"result": …}` rather than Markdown.
- The single highest-value, lowest-risk change on 2.x is to add `output_schema=None` to every `@app.tool(...)`, or one global strip middleware (Q2). Clients that read text then see raw Markdown, and structuredContent-preferring clients fall back to text because nothing else is present.
- Beware the "short `content` summary plus full `structuredContent`" pattern (`ToolResult`). On Codex, VS Code and Claude Code the model would see the full structured part, not the summary, which is the opposite of the intent.

### Gaps
- I did not measure the real token cost of escaped versus raw Markdown with a tokenizer; tiktoken's BPE download host was blocked.
- Whether any client passes `outputSchema` itself to the model is unverified. The Claude API tool format has only name, description and input_schema, so it is probably wire-only for Claude clients.

## Q5. FastMCP: how a docstring becomes a description, per-parameter descriptions, and schema compression

### Takeaway
In 2.x the **entire** docstring, including `Args:`/`Returns:` sections, is sent verbatim as the tool description, and per-parameter descriptions come only from `Annotated[...]`/`Field(description=...)`. From **3.2.4**, FastMCP parses Google, NumPy and Sphinx docstrings: the summary becomes the description, `Args` entries become per-property descriptions, and `Returns`/`Raises`/`Example` are dropped. Input schemas are already title-pruned in 2.x. 3.x adds `"additionalProperties": false` to input schemas, and 4.x always emits a tool `title`.

### Cited Findings
- Source (2.14.7): `fn_doc = inspect.getdoc(fn)` is used as `description=fn_doc`, with no parsing — [tool.py @ v2.14.7 (lines ~477, 578)](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py)
- Verified (test, 2.14.7): for a docstring containing summary, paragraph, `Args:` and `Returns:` blocks, the description was the full text `"Disassemble instructions.\n\nLonger explanation paragraph.\n\nArgs:\n    addr: Start address\n    count: Number of instructions\n\nReturns:\n    Markdown listing"`. The input schema properties had **no** `description` — [tool.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/tools/tool.py)
- Verified (test, 2.14.7): `Annotated[int, Field(description="Start address (hex ok)")]` and the shorthand `Annotated[str, "plain-string annotation"]` both produced property-level `description` fields. The docs date the shorthand to 2.11.0: "This shorthand syntax is only applied to `Annotated` types with a single string description" — [Tools docs](https://gofastmcp.com/servers/tools)
- **3.2.4 (2026-04-14)**: "Extract parameter descriptions from docstrings". Docs (VersionBadge 3.2.4): "Google, NumPy, and Sphinx docstring styles are all supported … The free-form text above the `Args` section … becomes the tool description, and each parameter's docstring entry becomes the description for that parameter … Sections like `Returns`, `Raises`, and `Example` are excluded". Explicit `Annotated`/`Field` descriptions take precedence — [FastMCP changelog](https://gofastmcp.com/changelog); [Tools docs, Docstring Descriptions](https://gofastmcp.com/servers/tools)
- Verified (test, 3.4.9): the same docstring produced `"description": "Disassemble instructions."` (the `Args:` block was removed; the paragraph test was only run on 2.x) and `"addr": {"type": "integer", "description": "Start address"}`. Implementation: `fastmcp/utilities/docstring_parsing.py` and `tools/function_parsing.py` — [function_parsing.py @ v3.4.9](https://github.com/PrefectHQ/fastmcp/blob/v3.4.9/src/fastmcp/tools/function_parsing.py)
- `compress_schema` signature in 2.14.7: `compress_schema(schema, prune_params=None, prune_defs=True, prune_additional_properties=True, prune_titles=False, dereference=False)`. "prune_additional_properties: Whether to remove additionalProperties: false" and "dereference: Whether to inline $ref references for client compatibility" — [json_schema.py @ v2.14.7](https://github.com/PrefectHQ/fastmcp/blob/v2.14.7/src/fastmcp/utilities/json_schema.py)
- Schema-related history: 2.3.4 "Prune titles from JSONSchemas"; 2.12.4 "Remove JSON schema title metadata while preserving parameters named 'title'"; 2.14.4 (2026-01-22) backported `$ref` dereferencing, and 2.14.6 (2026-03-27) actually wired it in ("`compress_schema()` dereferences at both tool schema creation sites"); **3.0.0b2 (2026-02-07)** "Fix compress_schema to preserve additionalProperties: false for MCP compatibility"; 3.0.0rc1 made dereferencing optional (`FastMCP(dereference_schemas=True)` by default); 3.2.4 "strip title fields from tool schemas for Gemini 2.5 Flash compatibility"; **4.0.0 (2026-08-31)** "Always emit a tool title, derived from name when unset" — [FastMCP changelog](https://gofastmcp.com/changelog)
- Verified (test): 2.14.7 input schemas have no `title` and no `additionalProperties`. 3.4.9 and 4.1.1 add `"additionalProperties": false` to input schemas. 4.1.1 adds `"title": "Disasm"` to every tool — [server.py @ v3.4.9](https://github.com/PrefectHQ/fastmcp/blob/v3.4.9/src/fastmcp/server/server.py); [FastMCP changelog v4.0.0](https://gofastmcp.com/changelog)
- The 3.x `DereferenceRefsMiddleware` exists because "Some MCP clients (e.g., VS Code Copilot) don't handle JSON Schema $ref properly" — [dereference.py @ v3.4.9](https://github.com/PrefectHQ/fastmcp/blob/v3.4.9/src/fastmcp/server/middleware/dereference.py)

### Inferences
- If binary-mcp docstrings contain `Returns:`/`Example:` sections, 2.x currently pays for them in every listing. Upgrading to ≥3.2.4 would strip them and move `Args:` text into per-property descriptions automatically. On 2.x you can get the same effect by writing short one-line docstrings and putting argument docs in `Annotated[..., "..."]`, or by passing `description=`.
- Dereferencing `$ref` can increase schema size when a model type is reused several times. This is unlikely to matter for binary-mcp's mostly scalar arguments.
- The 3.x and 4.x additions (`additionalProperties:false`, ~30 bytes, and auto `title`, ~15-25 bytes per tool) are small but real regressions for a 147-tool listing (an estimated ~7 KB). They should be weighed against the 3.2.4 docstring savings.

### Gaps
- Whether clients forward the tool-level `title` to the model is unverified.

## Q6. FastMCP 3.x and 4.x: what was released, when, and what matters for tokens; migration cost from 2.x

### Takeaway

### Inferences
- Migration 2.14.7 → 3.4.x for binary-mcp looks small. It needs the pin change, `get_tools()` → `list_tools()` in `tool_catalog.py`, and the `_meta` key change `_fastmcp` → `fastmcp`. In exchange it gains docstring parsing (3.2.4), visibility and per-session visibility, pagination, `ResponseLimitingMiddleware` and search transforms. 3.x still uses mcp 1.x, so `mcp[cli]>=1.6` is unaffected.
- Moving to 4.x additionally requires MCP SDK v2 (mcp 2.x) and pydantic ≥2.12. It also changes semantics: no per-connection tool lists on 2026-era clients, and no server-side sampling. The token-relevant extras over 3.4 are cache hints (`ttlMs`) and the stdio `list_changed` capability fix; the auto `title` is a small token regression.
- For a 147-tool server targeting VS Code (128 cap), Cursor (~40) and Windsurf (100), `BM25SearchTransform` with a handful of `always_visible` tools is the strongest single server-side lever available in FastMCP (3.1+). Its results return full JSON definitions by default, so a compact `search_result_serializer` (name, one-line description, compact params) should be supplied.
- On Claude Code, where tool search is built in, a server-side search transform duplicates client functionality and stops Claude Code from registering the tools natively. It is better to expose the real tools there, which suggests making the transform opt-in per client profile.

### Gaps
- The docs changelog lists 3.x only through 3.4.7 (2026-08-10); release dates for 3.4.8 and 3.4.9 were not found.
- Whether `ctx.enable_components` deliberately no-ops on 2026-era connections (rather than being a bug) is not stated in the visibility docs I read.

## Q7. MCP specification revisions 2025-06-18, 2025-11-25 and 2026-07-28: token-relevant rules (pagination, list_changed, outputSchema and structuredContent, resource_link, annotations, tasks, sampling and elicitation)

### Takeaway
2025-06-18 introduced structured output (with the SHOULD to duplicate it as text) and `resource_link`. 2025-11-25 added experimental tasks, tool-name guidance and sampling-with-tools. **2026-07-28** (final, released on that date) made MCP stateless, moved `list_changed` to `subscriptions/listen`, required `ttlMs`/`cacheScope` on list results, asked for deterministic `tools/list` order for prompt caching, moved tasks to an extension, and **deprecated Sampling** and Roots. None of the revisions adds tool search, groups or lazy schemas.

### Cited Findings
- **2025-06-18** major changes: "Add support for structured tool output" (PR #371); "Add support for elicitation" (PR #382); "Add support for resource links in tool call results" (PR #603); "Add `title` field for human-friendly display names" (PR #663); "Add `_meta` field to additional interface types" (PR #710); "Remove support for JSON-RPC batching" — [2025-06-18 changelog](https://modelcontextprotocol.io/specification/2025-06-18/changelog)
- Tools spec (2025-06-18): `tools/list` supports `cursor`/`nextCursor` pagination; `listChanged` "indicates whether the server will emit notifications when the list of available tools changes"; "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block"; and clients must treat tool annotations as untrusted unless they come from trusted servers — [Tools spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
- **2025-11-25**: icons (SEP-973); "Provide guidance on tool names (SEP-986)"; URL-mode elicitation (SEP-1036); "Add tool calling support to sampling via `tools` and `toolChoice` parameters (SEP-1577)"; "Add experimental support for tasks … durable requests with polling and deferred result retrieval (SEP-1686)"; "input validation errors should be returned as Tool Execution Errors … to enable model self-correction (SEP-1303)"; "Establish JSON Schema 2020-12 as the default dialect (SEP-1613)" — [2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- **2026-07-28**: "Remove protocol-level sessions … List endpoints (`tools/list`, `resources/list`, `prompts/list`) no longer vary per-connection. Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments (SEP-2567)"; "remove the `initialize`/`notifications/initialized` handshake" and add `server/discover` (SEP-2575); "Replace the HTTP GET endpoint and `resources/subscribe` … with `subscriptions/listen` … Clients opt in to specific types (`toolsListChanged`, …)"; tasks moved into the `io.modelcontextprotocol/tasks` extension (SEP-2663); Multi Round-Trip Requests replace server-initiated `sampling/createMessage`/`elicitation/create` (SEP-2322) — [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- 2026-07-28 minor changes: "Servers SHOULD return tools from `tools/list` in a deterministic order to enable client-side caching and improve LLM prompt cache hit rates"; "Require `ttlMs` and `cacheScope` fields on results returned by `tools/list` … via a new `CacheableResult` interface … complement existing `listChanged` notifications (SEP-2549)"; "Loosen `inputSchema` and `outputSchema` to allow any JSON Schema 2020-12 keywords, and `structuredContent` to allow any JSON value (SEP-2106)"; "Deprecate the Roots, Sampling, and Logging features (SEP-2577)… integrate directly with LLM provider APIs instead of Sampling" — [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- The 2026-07-28 tools page keeps the SHOULD-duplicate-as-TextContent rule. Its example `tools/list` result carries `"ttlMs": 300000`. Pagination: "Page size is determined by the server, and clients MUST NOT assume a fixed page size" — [Tools spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [Pagination 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination)
- Timeline: the 2026-07-28 release candidate was announced in May 2026, with beta SDKs, and the final release came on 2026-07-28. Vercel says "clients built for the 2025 protocol keep working exactly as before" — [MCP blog (release tag)](https://blog.modelcontextprotocol.io/tags/release/); [Vercel changelog](https://vercel.com/changelog/vercel-mcp-now-supports-the-2026-07-28-mcp-specification)

### Inferences
- `resource_link` is the spec's sanctioned way to return a pointer, for example `ghidra://function/0x401000/decompiled`, instead of inlining a large listing. Its token value depends entirely on whether the client lets the model fetch the resource later (Q9). Embedded resources (`type: "resource"`) still inline the content.
- Tasks (2025-11-25 experimental; a 2026-07-28 extension) address long-running calls and timeouts, not tokens. Sampling is deprecated as of 2026-07-28, and FastMCP 4 removed server-side sampling, so "summarize via client LLM" is not a durable token strategy.
- Deterministic tool order and stable definitions are now explicit spec guidance for prompt caching. binary-mcp should avoid reordering or rewording tools between calls, which also argues against frequent `list_changed` churn.

### Gaps
- I did not read the 2026-07-28 tool-annotations text in detail. Annotations add bytes and no token savings.
- The `instructions` delivery path under 2026-07-28 (`server/discover` versus a per-result `_meta`) was not verified.

## Q8. SEPs and proposals on token bloat or progressive tool discovery, and their status as of October 2026

### Takeaway
Every proposal to standardize tool groups, namespaces, lazy schemas, dynamic discovery or `tools/search` was **closed without entering the spec**. The spec's position, stated in the 2026-07-28 client best-practices guide and the Progressive Disclosure Working Group charter, is that progressive discovery is a **host-side** concern. The only accepted cache-related change is SEP-2549 (TTL on list results).

## Q9. Client support matrix (as of October 2026)

### Takeaway
**Claude Code** is the most capable client. It defers MCP tools behind built-in tool search by default, handles `list_changed`, and offers per-tool `_meta` knobs (`anthropic/alwaysLoad`, `anthropic/maxResultSizeChars`) and a 25k-token default output cap. Like **Codex** and **VS Code**, it feeds `structuredContent` to the model in place of text when both exist. **VS Code** caps requests at 128 tools and switches to "virtual tools" above that. **Cursor** (~40) and **Windsurf** (100) have hard-ish caps. **Gemini CLI** reads text content, supports `list_changed`, and truncates at 40,000 characters.

### Cited Findings

#### Claude Code (CLI; CHANGELOG at v2.1.303 on 2026-10-19)
- `list_changed`: "Added support for MCP `list_changed` notifications … without requiring reconnection" (2.1.0). "on a `list_changed` notification, Claude Code fetches the updated list"; "in `-p` mode and Agent SDK: only the tool list is refreshed". 2.1.271 fixed "sustained high CPU usage and repeated tool-list requests when an MCP server sends `list_changed` notifications in a tight loop" — [Claude Code CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md); [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Tool search: "Tool search is enabled by default: MCP tools are deferred and discovered on demand. … Only tool names and server instructions load at session start". "Claude Code doesn't impose a fixed per-server tool cap". `ENABLE_TOOL_SEARCH` accepts unset (deferred), `true`, `auto` ("loads … upfront while their definitions total less than 10% of the context window"), `auto:N` and `false`. Tool search is used on Opus 4, Sonnet 4, Haiku 4.5 and later, and is disabled for non-first-party `ANTHROPIC_BASE_URL` unless set explicitly. Auto mode became the default in 2.1.7, and `auto:N` arrived in 2.1.9 — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- Server-author knobs in a tool's `tools/list` `_meta`: `"anthropic/alwaysLoad": true` loads the tool upfront. The user can set `alwaysLoad` per server (2.1.121); `"alwaysLoad": false` defers all tools (v2.1.287+). `"anthropic/maxResultSizeChars": N` raises that tool's persist-to-disk threshold "up to a hard ceiling of 500,000 characters" (added 2.1.91). `"anthropic/requiresUserInteraction": true` forces an approval prompt. Verified (test, 2.14.7): FastMCP `@tool(meta={...})` emits these keys at top level of `_meta` — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Output limits: `MAX_MCP_OUTPUT_TOKENS` defaults to **25,000 tokens**, with a fixed warning at 10,000. Results "longer than **50,000 characters** are saved to a file regardless of token count", and the conversation gets the file path. Error text over ~11,000 characters keeps only the first and last 5,000 characters. HTTP responses over 16 MiB fail — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Descriptions: tool descriptions and server instructions are cut at 4,096 characters (upfront) and 16,384 (tool-search loaded); the override is `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` (v2.1.280+). Root-level `anyOf`/`oneOf`/`allOf` schemas are flattened. Tools with invalid schemas (property names outside `[A-Za-z0-9_.-]{1,64}`, or not valid 2020-12) are excluded (v2.1.216+). Mid-session tools "now receive [them] as deferred definitions" to preserve prompt cache (2.1.267) — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- structuredContent: the 2.0.21 entry reads "Support MCP `structuredContent` field in tool responses". A user report (open, 2026-10-19, Claude Code 2.1.299) says: "Claude Code forwards only `structuredContent` to the model when an MCP tool result contains both `content[].text` and `structuredContent`… (structuredContent became preferred in 2.0.21)". It adds that "Claude.ai web, the Claude Desktop chat, ChatGPT and Grok … all pass `content[].text` to the model", and cites #9962, where an Anthropic team member called it intentional. Related issues #45575, #55677 and #64316 were closed as `not_planned`, and #79944 is open (2026-07-21). Official docs do not state the rule — [Issue #103396](https://github.com/anthropics/claude-code/issues/103396); [#79944](https://github.com/anthropics/claude-code/issues/79944); [#45575](https://github.com/anthropics/claude-code/issues/45575); [#55677](https://github.com/anthropics/claude-code/issues/55677); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)
- resource_link: "MCP: resource_link tool results are now supported" (1.0.44). Resources: "Type `@` … Resources appear alongside files", and "Claude Code automatically provides tools to list and read MCP resources". Prompts become `/mcp__server__prompt` commands. Elicitation is supported in form and URL modes. Pagination is handled; a changelog fix covers "servers that repeat a pagination cursor being asked for the same page up to 20 times" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

- binary-mcp's 147 tools exceed VS Code's 128-per-request cap (virtual tools kick in), Windsurf's ~100 and Cursor's ~40. Server-side profiles (`include_tags` on 2.x) or a search transform (3.1+) are needed for those clients. Claude Code users mostly don't need them because tool search already defers definitions.
- On three of the four clients whose result handling I could verify or that are strongly reported (Claude Code, Codex, VS Code), FastMCP's default `-> str` handling means the model reads `{"result":"<escaped markdown>"}`. Setting `output_schema=None` normalizes all clients to plain Markdown.
- A runtime "load category" pattern that relies on `list_changed` works on Claude Code (tools arrive deferred, so they may need a ToolSearch step), Gemini CLI and Zed. It is unreliable on Cursor and unproven on Codex and VS Code, so it should be an optional enhancement over static profiles, not the only mechanism.
- For Claude Code specifically, the cheap server-side wins are concise descriptions with search keywords in the first part, an `instructions` block, `anthropic/alwaysLoad` on 3-6 core tools (for example open binary, list functions, decompile), and `anthropic/maxResultSizeChars` only on tools that must return large outputs.
